1. The short version

We built a phone agent in Google CX Agent Studio that answers questions about Salesforce orders. The caller says an order number and the phone number registered on that order. The agent checks both against Salesforce and, only if they match, reads out the status, dates and total.

Two pieces do the Salesforce work

Connector The secure line to Salesforce. It logs in with OAuth and runs the lookup. No password or token lives in the agent.

Python tool The gatekeeper. It cleans what the caller said, compares the phone number, counts failed tries, limits access to the caller's own account and returns only safe details.

Why not just let the AI call Salesforce?

An AI that writes its own queries can be talked into reading the wrong data, and it matches phone numbers badly ("(416) 555-0142" is not "4165550142"). Putting the rules in code means the AI cannot skip them.

The eight rules that mattered most
  1. Keep checks and business rules in a Python tool, not in the instructions.
  2. Let a connector hold the login (OAuth with the secret in Secret Manager). Never store a token or secret in the agent.
  3. In Salesforce choose the api scope (not "Full access"), enable the client credentials flow, and set a Run As user.
  4. In Google's connector dialog leave OAuth scopes empty. Salesforce rejects a scope in this flow.
  5. Test one hop at a time: Salesforce login, then connector, then Python tool, then the full call.
  6. Give the agent only what a tool returned. Never let it guess dates or facts.
  7. Make every failure audible: escalate with a spoken apology, never a silent hang-up.
  8. Never paste a key or secret into a chat or an export. If you did, rotate it.

2. Architecture

The transcript saver (chapter 5) uses the same path: the Python tool calls a second operation on the same connector, which writes one record to Salesforce when the call ends.

What happens on a call

  1. The agent plays a fixed greeting (callback, no AI call needed).
  2. It asks for the order number and the phone number, reading each back digit by digit to confirm.
  3. It calls authenticate_user. The tool builds one fixed lookup and calls the connector.
  4. The connector gets a token from Salesforce with OAuth, runs the lookup and returns the order with its account's phone.
  5. The tool compares the phone number (digits only), updates the variables and returns a short result: verified or not, plus the safe details.
  6. The agent reads the result out, or says the details do not match, or escalates to a person on a system error or after 3 failed tries.
  7. When the agent ends the call, the after-model callback first runs save_transcript, so the conversation is stored in Salesforce before the call closes.

4. Setup walkthrough

Do the parts in order and run the test at the end of each part before moving on. Most problems we met were in a lower layer than where they showed up.

4.1 Salesforce

Know your data first

  • Check the real objects, fields and sample counts before designing tools. For orders: OrderNumber is an auto-number with 8 digits (00000102); only the statuses Draft and Activated exist by default; EndDate is the order end date; an Activated order needs order items; the phone number lives on the Account.
  • No test data? Create a few clearly labelled records (we prefixed names with DEMO - ), in one transaction, with a cleanup script tested inside a rolled-back transaction first. Phone numbers in the fictional 555-01xx range.

The user the agent runs as

Create a dedicated integration user with a permission set: API Enabled, and read access only to the objects and fields the tools return (Order: number, status, dates, total, account id; Account: phone). For a quick demo an admin works but can read everything; replace it before production.

Create the External Client App

  1. Setup → External Client App Manager → New. Give it a name and a contact email. Turn on Enable OAuth. The callback URL is required by the form but unused here; any https placeholder works.
  2. On the Settings tab, OAuth Settings, select the scope Manage user data via APIs (api). Not "Full access (full)": that does not satisfy this flow.
  3. Still on the Settings tab, tick Enable Client Credentials Flow. Save.
  4. On the Policies tab click Edit. Tick Enable Client Credentials Flow, choose the Run As user, and set IP Relaxation to Relax IP restrictions (Google's servers have no fixed addresses; tighten later if you can). Leave Permitted Users and the refresh-token settings alone. Save.
  5. On the Settings tab open Consumer Key and Secret. Salesforce emails a verification code. Copy the key and the secret yourself and do not paste them anywhere public.
  6. Wait a minute or two. A new app or a changed scope can take a moment to apply.

Prove it before touching Google

In your own terminal (the prompts hide what you type, and the token is never printed):

printf 'Consumer key: '; read -rs SF_KEY; echo; printf 'Consumer secret: '; read -rs SF_SECRET; echo; export SF_KEY SF_SECRET
python3 ~/.claude/skills/ces-agent-builder/scripts/sf_oauth_check.py --org <alias> \
  --soql "SELECT Id,OrderNumber,Account.Phone FROM Order LIMIT 1"
Pass conditionOutput shows token issued: True, scope api, then QUERY: HTTP 200 with an order. On an error the script prints the likely cause and fix. Do not continue until it passes.

4.2 Google Cloud

  1. Enable the Secret Manager API in the project that owns the agent (APIs and Services → Library → Secret Manager API → Enable). It can take a few minutes to take effect. A console message "Secret Manager API has not been used in project ... or it is disabled" means this step is missing.
  2. Create the secret (Security → Secret Manager → Create secret). Name salesforce-client-secret; value = the Salesforce consumer secret with no trailing space or newline. Use a standard global secret (regional secrets are not supported here).
  3. Find the project number (Dashboard → Project info). The CX Agent Studio service account is service-<PROJECT-NUMBER>@gcp-sa-ces.iam.gserviceaccount.com.
  4. Grant it access to that one secret: the secret → Permissions → Grant access → the service account above → role Secret Manager Secret Accessor.
  5. Note the secret's version path: projects/<project-id>/secrets/salesforce-client-secret/versions/1. A new secret value creates a new version; select that version in the connector dialog.

The same from a terminal (the secret comes from the environment, never typed inline):

gcloud services enable secretmanager.googleapis.com --project=<project-id>
printf '%s' "$SF_SECRET" | gcloud secrets create salesforce-client-secret --data-file=- --replication-policy=automatic --project=<project-id>
gcloud secrets add-iam-policy-binding salesforce-client-secret \
  --member="serviceAccount:service-<PROJECT-NUMBER>@gcp-sa-ces.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor" --project=<project-id>

The Python tool

  • Name authenticate_user, lowercase snake_case, matching the reference in the instructions exactly.
  • It takes order_number and phone_number, builds the fixed lookup, calls the connector, compares the phone number in code, updates the four variables and returns a small result.
  • Result contract: success has verified: true and the details. Failures have error (not_verified, invalid_input, locked_out, salesforce_auth_failed, salesforce_error, tool_error) and a short message. System problems add system_error: true.

Instructions, callbacks, guardrails, model

  • Instructions: structured (role, persona, constraints, task flow). Name the tool with {@TOOL: authenticate_user}.   • Guardrails: keep the two defaults and check that each toggle is on. Add an LLM policy only for rules that must never break (it adds delay to every reply).
  • Model and voice: gemini-composite-v2 with a Chirp 3 HD voice.

5. Saving the call transcript to Salesforce

Goal: when a call ends, the whole conversation is stored in one Salesforce record, linked to the order and the account, so a person can read it later. Verified in Preview A call finished in the Preview simulator saved a record with the right outcome, turn count, duration and links.

5.1 How it works

  1. The agent decides the call is over and asks to run end_session: finished, escalated or a system problem.
  2. An after-model callback sees this and puts a save_transcript call in front of end_session, with the outcome (completed, escalated or system error).
  3. With sequential tool execution the save runs first and finishes before the call ends.
  4. The save_transcript Python tool builds the text from the session's events, one Caller: or Agent: line per turn. It masks card and social security number patterns, cuts anything past 120,000 characters, and adds start, end, duration, turn count, the verified flag and the order and account ids kept in variables.
  5. It calls the connector's save_transcript operation, which creates the record or, if that session id was saved before, updates it. One call, one record.

5.2 What was built

PieceWhat it is
Salesforce object Voice_Call_Transcript__cEleven fields: Session_Id__c (the unique key), Transcript__c (long text), start and end time, duration, turn count, Outcome__c (picklist: Completed, Escalated, Verification failed, System error, Unknown), Caller_Verified__c, Agent_Name__c and lookups to the order and account.
Permission set Voice_Agent_Transcript_WriterCreate and edit on that object only. Assigned to the Run As user of the External Client App.
Connector operation save_transcriptAdded to the schema of the same connector (query_salesforce). A PATCH on /sobjects/Voice_Call_Transcript__c/Session_Id__c/{session_id}; the body allows only the object's fields.
Python tool save_transcriptOn the Root agent's tool list, never mentioned in the instructions. Its description says it runs automatically and the agent must not call it.
After-model callbackOn the Root agent. Adds the save call in front of end_session.
Tool execution modeApp settings, Tools, Execution mode: Sequential.
No new variablesThe tool reads the four variables the verification tool already writes. The order and account links come from verified_record_id and verified_scope_id.

5.3 Steps in the console

Deploy the Salesforce object and permission set first (check-only deploy before the real one). Then, in this order:

  1. Connector: replace the Salesforce tool's schema with the version that has two operations, find_order and save_transcript. Leave authentication alone.
  2. Python tool: create save_transcript and paste the code. In Test Tool expect invalid_input or empty_transcript (no real session there); that only proves the code loads.
  3. Agent: add save_transcript to the Root agent's tools.
  4. Callback: add the after-model callback to the Root agent last, so it never refers to a tool that does not exist yet.
  5. Execution mode: set it to Sequential in the app settings.
  6. Test: run a full call in Preview, then look in Salesforce.
sf data query -o <alias> -q "SELECT Id, Session_Id__c, Outcome__c, Turn_Count__c, Duration_Seconds__c, Order__c, Account__c FROM Voice_Call_Transcript__c ORDER BY CreatedDate DESC LIMIT 5"

5.5 What we learned

Found in the real record

  • Caller lines began with <context>agent speaking was interrupted. user only heard '...'</context> whenever the caller talked over the agent. The tool now strips these notes. If you pasted the first version of the tool, replace its code.
  • Preview session ids start with simulator-, which separates test calls from real ones.

Confirmed by the console export

  • The tool, the callback and the new connector operation were exported exactly as pasted.
  • Callbacks are stored as after_model_callbacks/after_model_callbacks_01/python_code.py, so a folder name does not tell you what a callback does.
  • Sequential execution is the app setting toolExecutionMode: SEQUENTIAL.
Known gap: a caller who hangs up is not savedThe save runs only when the agent itself ends the call. If the caller hangs up first, no record is written. Pulling finished sessions through the Conversations API would cover this; it would use the same session id, so no duplicates. On a real phone line this matters more than in Preview.

5.6 Privacy

  • A transcript holds personal data and sometimes health or payment details. Restrict the object (sharing and field-level security), decide a retention period, and decide who may read it.
  • On voice, a recording or transcription notice to callers is usually required. The greeting callback can speak one.
  • Card and social security masking is a safety net, not a guarantee. Google's own log redaction does not cover the copy stored in Salesforce.
  • The tool prints counts and status only, never the transcript text.

6. Getting a phone number for the agent

From Google's documentation and pricing page We have not provisioned a number or placed a call. Check the current pages before you rely on any detail.

6.1 The route

CX Agent Studio can give an agent its own number through a Google Telephony Platform (GTP) channel. No Twilio or carrier is needed to start.

  1. Enable the Dialogflow API in the project and make sure the agent has a saved version. The channel deploys a version, not the draft.
  2. In the agent open Deploy, then Connect to a platform (or + New channel if there is one already).
  3. Name the channel and set Platform to Google Telephony Platform (GTP).
  4. Set Connection type to the standard PSTN option. The default is a virtual number, which an ordinary phone cannot dial.
  5. Choose the version. Optionally set channel behaviour: response length, keypad (DTMF) input, interruptions.
  6. Click Create channel. The console shows the number. Call it to test, then click Done.

6.4 What changes in the agent on a phone line

  • Caller's number: it arrives in a variable named exactly telephony-caller-id (type Text) if you declare it. It can be spoofed, so keep the order number and phone check; it could be saved with the transcript.
  • Handing over to a person: Google's way is two variables, telephonyTransferCall (an object holding phoneNumber in E.164 format) and optionally escalationMessage, plus end_session with escalation set. What our agent's escalation does on a phone line without them has not been tried.
  • Ending calls: end_session must be on the agent. It already is.
  • Order numbers by voice: keypad input (DTMF) can be switched on in the channel behaviour.
  • Hang-ups leave no transcript (chapter 5).
  • A public number: anyone who has it can call, and each call is billed. Details are only given after verification.

8. Security lessons

Secrets

  • Never put a token or secret in an agent file, a variable default, a chat or a ticket.
  • Exports write variable defaults in plain text. Validate before sharing.
  • A pasted secret is an exposed secret: regenerate it, add the new value as a new Secret Manager version, select that version.
  • Enter keys with a hidden prompt (read -rs), not on the command line, so they stay out of history.

Least privilege

  • The agent can do whatever the Run As user can. Create a dedicated user with read-only access to only the needed fields.
  • Grant the secret role on the one secret, not the project.
  • Keep sensitive fields (birth date, financial, health) out of what tools return.
  • Relaxed IP settings are a demo convenience; tighten them for production.

Deterministic controls

  • Verification, lockout and scope live in code and variables, not in prose.
  • The connector is hidden from the model.
  • One failure message for every wrong answer.
  • Write tools (if any) need an explicit caller confirmation flag and a field whitelist.

Transcripts

  • They hold personal data. Restrict who can read the object and set a retention period.
  • Tell callers they are being recorded or transcribed where the law requires it.
  • Masking of card and social security numbers is a safety net, not a guarantee.
  • The integration user needs create and edit on the transcript object and nothing else.

A public phone number

  • Anyone who has the number can call, and every call is billed. Watch usage and set a budget alert.
  • The caller's number can be spoofed. Never treat it as proof of identity.
  • Give details only after the two-detail check, exactly as in Preview.

Honest limits

  • A query pattern in the connector schema is defence in depth; whether the platform enforces it is unproven.
  • Guardrails reduce risk; they do not replace the controls above.
  • Recording and redaction settings are a policy decision to make deliberately.

9. Checklists

Best practices

  • One tool per business task; the tool does the whole job. Never chain tools in the instructions.
  • Distinct, verb-first, lowercase snake_case tool names; parameters flat, typed and well named.
  • Return only what the agent needs, in a stable result shape (ok, error, message, system_error).
  • Configuration in static variables ({{company_name}}), call state in variables written by tools ({caller_verified}).
  • Instructions: role, persona, numbered constraints, task flow; every step has a trigger and an action; every tool result is handled.
  • Voice: short sentences, one question at a time, read digits one by one, confirm numbers before using them.
  • A fixed greeting and a spoken escalation, both as callbacks.
  • If a callback adds a tool call next to end_session, set tool execution to sequential.
  • Keep internal tools (such as the transcript saver) out of the instructions and say in their description that the agent must not call them.
  • Guardrails: the two defaults enabled, plus only the extra rules that must never break.
  • Test each layer separately; keep a regression test for every bug found.

Before go-live

  • Run As user is a dedicated least-privilege user; IP relaxation tightened as far as possible.
  • Any secret that appeared in a chat or document has been rotated.
  • The latest export has been validated and contains no secrets.
  • Each guardrail's toggle is on; model and voice chosen; recording and redaction policy decided.
  • Failure paths tested: wrong details, lockout, empty secret, Salesforce unreachable.
  • A version snapshot taken; channel and modality set in the deployment.
  • Test data removed or clearly separated from real data.
  • Transcripts: who can read the object, the retention period and the caller notice are decided; the hang-up gap is accepted or covered.
  • Phone number: a real call from outside has been tested; cost, region and a budget alert are checked; the transfer number for escalation is set if people take over calls.

10. How we tested it

MethodWhat it proved
Offline scenarios for every toolCorrect details, wrong details, blank value, unknown order, lockout, empty input, 401 and 500 replies, no token in any result, no query injection.
Read-only runs against real dataThe query text, the field names and the result mapping work against the real org, with no token handled by the test. Wrong phone and a no-phone account were refused; another account's data was not reachable.
Deliberate breakageThe tests were run against copies of the tool with a safeguard removed (escaping, the verified gate, attempt counting, scope filter, a leaked token, the 401 mapping). Each was caught.
Comparison with real exportsThe files our generator writes were compared with three exports from the console. The latest confirmed where callbacks are stored and how sequential execution is saved, and showed the console keeps our tool, callback and connector operation exactly as pasted.
Behaviour tests for callbacksEach callback template is run against a faked CX runtime: greeting, escalation, silence prompt, redaction, mandatory text, the end-of-call save and hiding a tool. Deliberately broken copies were caught.
Read-only check after a test callA query on the transcript object showed the record the Preview call created: outcome, turn count, duration and links were right. Reading the saved text exposed the interruption notes that the tool now strips.
Salesforce login on its ownFound the empty variables, the missing scope and the scope-parameter problem before Google was involved.
Test Tool and Preview in the consoleThe final design works: verification, answer, and the failure paths.
Still unproven
  • Whether Google enforces the pattern that locks the connector's query.
  • The folders for before-model, agent and tool callbacks, and the non-default guardrail types, in a generated import package (the after-model layout is confirmed by an export).
